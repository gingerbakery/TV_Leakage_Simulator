# 최대 반사 횟수와 결과 수렴 확인

업데이트: 2026-09-08 · 반사 상한 확장 1차 · 허용 범위 `0~1000`

## 무엇이 바뀌었나

- `Ray tracing → Max reflections`에서 1,000회까지 입력한다.
- CPU, CUDA-resident, API 입력, `.bitsam` 저장/복원이 같은 상한을 사용한다.
- 기본값, 반사율, 광원 입력, 광량 집계 및 `nit_est` 환산식은 이번 변경에서 바꾸지 않았다.
- 반사 횟수는 전체 광선의 합이 아니라 **광선 하나가 반사할 수 있는 최대 횟수**다.
- Receiver 도달, 구조 밖 탈출, 에너지 종료가 먼저 발생하면 그 지점에서 끝난다. 1,000을 입력해도 모든 광선이 1,000번 반사하는 것은 아니다.

## 실측/LightTools와 비교하는 순서

1. CAD/ROI, 광원 위치·총 광속·분포, Receiver 위치·수광 방향·크기·격자, 표면 특성 및 입사각 반사율 옵션을 고정한다.
2. Ray 수, seed, Minimum energy, termination 설정도 고정하고 상한만 `20 → 50 → 100 → 300 → 1000`으로 올린다.
3. Receiver 총 광속(lm), 평균 조도(lux), 평균/peak `nit_est`를 함께 기록한다. Peak 하나만으로 판정하지 않는다.
4. `Result → Multi-bounce`에서 아래 진단값을 비교한다.
5. 상한 증가에 따른 광량 차이를 표본 오차와 함께 평가한다. Ray 수에 대한 통계적 수렴과 반사 상한에 대한 수렴은 서로 다른 검증이다.

| 진단값 | 의미 | 해석 주의점 |
|---|---|---|
| Reflection limit | 이번 계산의 허용 상한 | 설정값이지 실제 발생 횟수가 아니다. |
| Max observed depth | 실제 관측된 최대 깊이 | 상한보다 훨씬 작으면 상한 증가만으로 해결되지 않을 가능성이 높다. |
| Depth-limit stops | 상한에 도달해 다음 반사를 추적하지 못한 경로 수 | 건수만으로 누락 광량을 알 수 없다. 약한 경로가 많을 수도 있다. |
| Below-energy events | 반사 후 Minimum energy 아래로 내려간 횟수 | Threshold에서는 종료, Russian roulette에서는 일부가 가중치를 조절해 계속될 수 있다. |

총 광속이 더 이상 변하지 않는데 실측과 차이가 크다면 광원/Receiver 정의, ROI 밖 경로, 표면 모델, 절대 보정 조건을 먼저 검토한다. 상한 확장이 실측 일치를 보장하지는 않는다.

## 낮은 반사율에서도 1,000회가 필요한가

추가적인 방향/입사각 효과가 없고 매번 같은 반사율 `rho`를 쓰는 단순 경로라면, N회 반사 후의 광량은 `입력 광량 × rho^N`이다.

- 이번 검증용 거울은 `rho=0.999`이며 1,000회 후에도 입력의 약 36.77%가 남는다.
- 낮은 반사율에서 반복 반사한 경로는 훨씬 빠르게 약해질 수 있다.
- 실제 프로그램의 `Angle-dependent reflectance`, 혼합 산란, 중요도 표본 가중치가 활성화되면 위 단순식과 직접 비교하면 안 된다.
- Minimum energy는 ray당 광속 기준이다. 같은 총 광속에서 Ray 수를 늘리면 ray당 초기 광속이 작아지므로, 에너지 종료 조건도 확인해야 한다.
- 이번 작업에서 보정 상수나 반사율을 임의로 올려 결과를 맞추지 않았다.

## 속도와 메모리

- 반사 상한을 높이면 실제로 살아남는 경로와 저장 이력이 늘어 계산이 길어질 수 있다.
- 실제로 일찍 끝나는 경로라도 깊이별 GPU 버퍼 준비 비용은 늘 수 있으므로, 모든 해석의 기본값을 1,000으로 올리는 것은 권장하지 않는다.
- 큰 깊이에서는 한 번에 처리하는 Ray 수를 자동으로 줄인다. **전체 요청 Ray 수나 반사 상한은 줄이지 않는다.**
- 배치별 `Ray capacity × (max_depth+1)`을 2,097,152 event slot 이내로 제한한다. GPU의 2의 거듭제곱 버퍼 할당까지 고려한다.
- 기본 GPU 배치 65,536개는 상한 20에서 유지된다. 상한 100에서는 최대 16,384개, 상한 1,000에서는 최대 2,048개씩 처리한다.
- 이 제한은 주된 이벤트 버퍼 보호 장치다. CAD/BVH, 결과 격자, 경로 저장, CPU 복사본 등 **프로그램 전체 메모리의 절대 상한**은 아니다.
- 복잡한 CAD와 많은 실제 반사는 오래 걸릴 수 있다. 대량 비교 시 저장 경로 수를 줄이고 적은 Ray 수로 먼저 확인한다. OS의 GPU timeout이나 장치 메모리 부족이 발생하면 기존 실패/대체 실행 진단을 확인한다.

## 파일 호환과 실행 위치

- 기존 `0~20` 설정을 가진 `.bitsam` 파일은 그대로 사용할 수 있다.
- 1,000회 설정 저장/복원을 검증했다. 반사 상한이 20인 구버전으로 다시 열면 설정이 제한될 수 있으므로 최신 코드로 열어야 한다.
- 이번 구현 위치는 별도 `TV leakage simulator main` 작업폴더다. 렌더링 작업폴더나 이미 실행 중인 서버, 별도 EXE/ZIP에는 자동 반영되지 않는다.
- GPU 소스 실행은 이 폴더의 `run_web_gpu.bat`/`run_web_gpu.ps1`을 사용한다. 다른 작업의 서버가 사용 중인 포트는 공유하지 않는다.
