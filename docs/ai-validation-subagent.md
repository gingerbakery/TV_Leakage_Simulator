# 개발 / 독립 검증 서브 에이전트 운영 수칙

## 1. 목적과 적용 범위

메인은 설계·구현·통합을 담당하고, 검증 담당은 그 변경과 근거를 독립적으로
검토한다. 속도 향상이 해석 결과의 오류를 가리지 않도록 하는 것이 목적이다.
방법 A, 즉 현재 대화에서 업무를 위임하고 결과를 다시 통합하는 방식을 사용한다.

문서만으로 파일 접근을 강제 차단하는 것은 아니다. 명시적인 작업 범위,
고정된 입력, 시작 시 수칙 확인, 종료 시 hash 대조와 메인의 검토를 함께 적용한다.
별도 AI 세션도 같은 오류를 놓칠 수 있으므로 독립 계산 기준과 실행 증거가 필요하다.

- 사용자가 위임을 요청한 작업에서 검증 담당 한 명으로 시작한다.
- 별도 허용 없이 하위 에이전트를 만들거나 검증 범위를 계속 확대하지 않는다.
- 임무가 끝나면 결과와 미해결 항목을 기록하고 종료한다. 상시 감시로 간주하지 않는다.
- 공통 `AGENTS.md` 및 해당 경로의 하위 지침이 함께 적용된다.
- 이 수칙이 기존 GPU 실행·보안·승인 규칙을 완화하지 않는다.

## 2. 역할과 변경 권한

| 담당 | 기본 허용 | 기본 금지 |
| --- | --- | --- |
| 메인 | 요구사항, 구현, 검증 대상 고정, 수정 제안 검토, 통합 | 실패·미검증 항목을 통과로 포장 |
| 검증 담당 | 고정 소스·테스트·로그 읽기, 계산 근거 확인, 재현 절차와 결함 보고 | 제품 소스, 기준 결과, 허용 오차, 사용자 파일 수정 |

검증 담당의 테스트·보고서 작성이 필요하면 정확한 파일 또는 출력 디렉터리를
별도로 허용한다. 메인의 수정 범위와 겹치지 않게 한다. 제품 오류는 메인에게
전달하고, 메인이 수정한 새 snapshot에서 영향받는 검증을 다시 수행한다.

양쪽 모두 사용자 요청 없이 commit, push, branch 생성, merge, 배포, 서버
시작·종료·재시작, 환경 재설치, driver/Toolkit 설치, 시스템 설정 변경,
재부팅을 하지 않는다. 기존 서버, 사용 중인 `.bitsam`, 원본 CAD와 사용자
입력값은 검증용으로 덮어쓰지 않는다. Git 상태를 임의로 정리하거나 되돌리지 않는다.

## 3. 위임 전 메인의 준비

[`validation-handoff.md`](templates/validation-handoff.md)를 기준으로 다음을 명시한다.

1. 임무 ID, 구체적인 질문, 종료 조건, 범위 밖 작업.
2. delivery path, 절대 repository 경로, branch와 commit, 미커밋 변경 유무.
3. 검증 snapshot 경로, manifest 경로와 SHA-256, baseline 식별자.
4. 입력 CAD/프로젝트/config/seed/ray 수/반사 상한 등 필요한 재현 조건.
5. 읽기 범위, 쓰기 허용 목록, 허용 명령 종류, 실행 시간·자원 상한.
6. 실행 전 정한 지표별 통과 기준과 기준의 출처.
7. 메인이 동시에 수행할 별개 작업과 CPU/GPU 측정 담당자.
8. 제출할 근거, 불확실성, 다음 조치의 형식.

### 버전 고정

- commit만 같다고 실행 코드가 같다고 간주하지 않는다. 미커밋·미추적 변경도
  검증에 사용한다면 snapshot에 포함하고 파일별 SHA-256을 기록한다.
- manifest에는 포함 파일, 크기, hash, 수집 시각, 원본 경로와 누락/제외 범위를
  남긴다. 기존 로그는 해당 로그를 만든 코드와 연결되는지 별도로 확인한다.
- snapshot은 검토 중 수정하지 않는다. 변경된 checkout에서 계속 개발할 수 있지만
  그 새 변경에 과거 snapshot의 통과 판정을 적용하지 않는다.
- 시작·끝에 입력 hash를 비교한다. 누락 또는 불일치 시 해당 검토를 중단하고
  `BLOCKED`로 보고한다. 새 snapshot은 새 임무 ID로 구분한다.
- 기존 테스트 결과의 수집일과 이번 검토일을 구분한다. 결과 파일만 복사했다고
  이번에 테스트를 다시 실행한 것으로 표현하지 않는다.
- snapshot이 실행 가능한 전체 환경인지, 일부 파일만 담은 문서 검토 묶음인지
  명시한다. 실행용 의존성·fixture가 없으면 실행 검증을 주장하지 않는다.

## 4. 검증 담당의 시작 확인

본격적인 검토 전에 다음 항목을 메인에게 알린다.

- 읽은 지침과 임무 ID.
- snapshot / manifest 식별자, hash 대조 결과.
- 쓰기 허용 범위와 금지 작업.
- 검토 모드와 자원 사용 제한.
- 판정 기준, 빠진 입력, 충돌하거나 불명확한 지침.

필수 입력이나 기준이 불명확하면 추측하여 통과시키지 않는다. 영향을 받는
항목을 `BLOCKED` 또는 `NEEDS_RUN`으로 분리하고 해결에 필요한 정보를 요청한다.

### 모델 선택과 진행 표시

사용자가 모델 배치를 위임한 경우 메인은 작업별로 모델과 추론 강도를 명시한다.
기본 검토는 `gpt-6.1-sol / high`, 어려운 물리·수치 불일치 검토는
`gpt-6-astra / high`(필요 시 `xhigh`), 단순 로그·문서 대조는
`gpt-6-luna / medium`을 사용한다. 동시 검증 담당 한 명 원칙은 유지한다.
해당 모델을 사용할 수 없으면 실제 대체 모델을 알리고 기록한다.

검증 담당은 시작 메시지에 실제 지정 모델·추론 강도·임무·총 점검 항목을
명시한다. 단계가 바뀔 때 완료 항목 수, 현재 작업, 측정한 경과 시간과 갱신
시각을 짧게 알린다. 단순 항목 비율을 예상 잔여 시간으로 해석하지 않으며
측정하지 않은 진행률·시간을 만들어내지 않는다. 이 메시지는 내장 서브 작업
화면에서 확인하는 기록이며, 별도 창이나 초 단위 현황판을 보장하지 않는다.

## 5. 검토 모드와 자원 사용

### `evidence_only` — 기본 모드

소스·기존 로그·JSON·보고서를 읽고, hash·수치·보고서 주장과 근거를 비교한다.
읽은 소스를 실행하거나 import하지 않는다. 임의의 테스트·CUDA preflight·
서버 API 호출·benchmark·build·package 설치를 실행하지 않는다. 단순한 파일
읽기, hash 계산, JSON 수치 재계산은 허용한다. GPU 사용·성능은 **기존 실행
기록에 대한 확인**이며 현재 PC의 새 실행 성공으로 보고하지 않는다.

### `test_execution` — 명시적으로 허용된 경우

메인이 지정한 테스트·명령·출력 경로·상한만 사용한다. GPU 관련 작업은 먼저
아래 세 문서를 모두 읽고 그 규칙을 따른다.

- `ai-gpu-execution-runbook.md`
- `gpu-cuda-user-guide.md`
- `WINDOWS_GPU_SETUP.md`

무거운 CPU/GPU 성능 측정은 한 번에 한 담당자만 실행한다. 메인은 같은 시간에
다른 측정이나 빌드를 시작하지 않는다. 수동 사용 또는 다른 프로세스의 부하가
발견되거나 자원 독점 여부가 불확실하면 측정을 미루고 오염된 결과는 제외한다.
worktree·포트·AI 세션이 달라도 하드웨어는 공유할 수 있다.

최초 실행과 warm 2~3회를 구분하고 같은 장면·입력·세션을 비교한다. JIT,
형상 준비, 순수 추적, 집계, 전체 wall time을 섞어 가속률을 만들지 않는다.
명시된 시간·자원 상한에 도달하면 중단하고 부분 결과와 후속 계획을 보고한다.

## 6. 정확도와 판정 기준

기준은 실행 전에 지표별로 정한다. 결과를 보고 허용 오차를 바꾸거나 실패한
필드를 제외해 통과시키지 않는다. 기준 수정이 정말 필요하면 원래 실패를
보존하고 이유·영향을 메인에게 제출한다. 새 기준은 별도 검증으로 기록한다.

- **이산 결과:** 동일 샘플 계약에서는 Ray 수, hit 수, 경로 분기 등 명시된
  항목의 exact 일치를 검사한다. 의도적으로 샘플을 바꾸는 실험은 따로 구분한다.
- **수치 결과:** Receiver flux, heatmap, peak, 평균, 분산과 보조 집계를
  구분한다. 절대/상대/ULP 기준의 결합 방식, 단위, near-zero 처리를 명시한다.
- **반복성:** 수정 전끼리, 수정 후끼리, 전후 비교를 구분한다. 단일 seed의
  일치와 여러 seed의 통계적 수렴은 서로 다른 검사다.
- **물리 정확성:** CPU/GPU 일치만으로 정답이라 하지 않는다. 광량 보존,
  알려진 해의 단순 모델, 반사율·반사 분포·단위 계약을 별도로 확인한다.
- **LT/실측:** 입력과 측정 조건이 맞춰진 비교 근거가 없으면 미검증으로 남긴다.
  추정 nit와 실제 측정 휘도를 같은 의미로 다루지 않는다.
- **GPU 실행:** preflight와 실행 state, CUDA 성공/시도, CPU hybrid/fallback
  근거가 필요하다. `BVH` 표시만으로 GPU 실행을 판정하지 않는다.
- **통과 범위:** 일부 fixture 또는 Receiver만 통과한 결과를 전체 CAD, 모든
  광원/반사/보조 집계, 전체 제품의 완료로 일반화하지 않는다.

## 7. 보고와 종료

각 결론에는 파일·필드·수치·재현 조건을 붙인다. 가능한 결함은 영향도, 증거,
실제 오류인지 증거 부족인지, 필요한 재현 또는 수정 방향으로 정리한다.

| 판정 | 의미 |
| --- | --- |
| `PASS` | 명시한 범위와 기준에 한해서 근거 충족 |
| `FAIL` | 명시한 기준 위반이 근거로 확인됨 |
| `NEEDS_RUN` | 실행하지 않았거나 기록만으로 결론을 낼 수 없음 |
| `BLOCKED` | 입력/버전/권한/자원/기준 문제로 유효한 검토 불가 |
| `OUT_OF_SCOPE` | 이번 임무 대상 아님; 통과 개수에 포함하지 않음 |

전체 판정과 항목별 판정을 구분한다. 필수 항목에 FAIL/BLOCKED/NEEDS_RUN이
있으면 전체 통과라고 하지 않는다. 검토한 파일, 실행한 명령, 새 실행 여부,
미해결 항목, 입력 hash 유지 여부를 함께 제출한다.

메인은 핵심 근거를 직접 대조한 뒤 채택·보류·추가 검증으로 결정한다.
보고서는 `docs/reports/`에, 크거나 사용자 형상을 포함하는 로컬 근거는
Git에서 제외된 `outputs/validation/`에 둔다. 로컬 근거를 자동 업로드하지 않는다.
사용자에게 현재 적용 범위와 다음 조치를 알리고 임무를 종료한다.
