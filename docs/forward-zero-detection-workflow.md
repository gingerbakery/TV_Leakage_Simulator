# 실물에서는 보이지만 순방향 검출은 0인 경우의 작업 순서

현재 source checkout의 기능을 기준으로 한다. 목적은 광원·형상 조건 문제, 경로 재현 문제, 표본 부족, 센서 조건 제외, 보고/표시 문제를 구분하는 것이다. CPU/GPU 계산끼리 일치하는 것과 실물 정확도 검증은 별개다.

## 1. 새 버전 실행과 조건 고정

진행 중 해석을 마치거나 정상 중지한 뒤 프로그램을 종료하고 최신 소스로 다시 실행한다. 다른 PC에서는 먼저 최신 `main`을 받는다. GPU 실행은 `run_web_gpu.bat`을 사용하고 준비 완료 상태를 확인한다. 기존 ZIP/EXE는 Git 갱신만으로 바뀌지 않는다. GPU 실행 준비는 [GPU 가이드](gpu-cuda-user-guide.md)를 따른다.

기준 프로젝트를 별도 이름으로 저장하고 실물에서 보이는 위치·관찰 방향을 기록한다. 광원·재질·Block·해석 제외·Allowed 영역·ROI·최대 반사·에너지 종료 조건을 대조할 때까지 고정한다.

## 2. 순방향과 Preview의 광원 맞추기

Ray Tracing에 실제 검증에 사용할 광원을 먼저 등록·확인한다. 출력, 방출 방향, 분포, Aim, 활성 광원을 확인한다. Preview에서는 `기존 Emitter 사용`으로 동일한 광원만 선택한다. Preview는 그 광원을 복사해 표본 수만 배분하며 원본 조건은 유지한다.

Preview의 `Body` 직접 선택은 선택 Body의 실제 CAD 표면에 **양면 Lambertian 등가 광원**을 만든다. 외접 사각 Plane은 생성하지 않는다. 실제 발광이 한쪽 방향이거나 다른 배광이면 동일 조건이라고 간주하지 않는다. Body 직접 선택으로 검사하던 경우에는 새 버전에서 Body를 선택하고 Preview를 새로 실행한다. 이전 저장 결과나 저장된 가상 Plane Emitter는 자동 변환되지 않는다.

`순방향 진단 준비`는 Receiver와 진단 설정을 준비하는 버튼이다. Preview의 광원을 Ray Tracing의 등록 광원으로 복사하는 버튼은 아니다. 같은 광원에서 시작하려면 위의 `기존 Emitter 사용` 경로를 이용한다.

## 3. Preview 재실행과 Point 선택

표시 필터에서 `초기화`를 누른다. 처음 원인을 찾을 때는 최대 반사·최소 nit·최소 밝기 필터로 후보를 숨기지 않는다. 이 필터는 표시만 바꾸며 원본 검출·광량을 바꾸지 않는다.

실물 관찰 방향에 맞춰 Preview를 실행하고, 완료 후 해당 위치의 Point를 선택한다. 여러 Point가 묶여 있으면 개별 Point 하나를 선택한다. 이전 결과를 재사용하는 대신 현재 입력으로 새 결과를 만든다. 해당 위치가 Preview에서도 검출되지 않으면 대표 경로 재생은 진행할 수 없으며 광원·관찰 조건 및 Preview 미검출부터 확인한다.

실행 중에는 처리 단계와 완료 표본 수를 확인한다. `진행 갱신 없음`은 마지막 단계·수치 변경 이후 경과 시간이며 정지 확정은 아니다. 장시간 변하지 않으면 단계·완료/전체 표본 수·경과 시간과 서버 로그를 기록하고 중지를 요청한다. 중지는 진행 중 배치가 끝난 경계에서 처리된다.

## 4. 경로 검증과 순방향 재생

선택 Point에서 `경로 검증`을 누른다. 완료하면 경로 조건 검사 결과와 `대표 경로 순방향 재생` 항목이 나온다. 재생을 위한 별도 실행 버튼은 필요 없다. 항목을 펼쳐 첫 불일치 구간·좌표, 일치 반사점 수, 실제 센서 도달·제외와 종료 조건을 확인하고 `재생 JSON 저장`을 누른다.

| 결과 | 다음 작업 |
| --- | --- |
| 경로 검증 실패 | 표시된 광원·차폐·재질·반사 한도·Receiver 불일치를 먼저 확인한다. 표본 증가로 해결하려 하지 않는다. |
| 동일 경로 도달 | 저장 경로가 진단용 순방향 1 Ray로 재현됐다. 다음 광량 비교를 진행한다. 일반 발사에서 그 경로가 충분히 표본화됐다는 뜻은 아니다. |
| 확률적 반사 분기 변경 | 실제 확산/확률 반사가 다른 방향을 뽑았다. 곧바로 오류로 판정하지 않고 광량 비교의 독립 반복 결과를 본다. |
| 에너지 컷오프·최대 반사·확률적 종료 | 어떤 조건이 해당 진단 Ray를 종료했는지 기록하고, 광량 비교의 기존 종료 조건 진단과 대조한다. |
| 충돌 위치 불일치 | 첫 불일치 구간과 예상/실제 좌표를 저장한다. 형상·좌표·epsilon 출발 오프셋·반사 계산을 조사할 근거다. |
| 중첩 광원 식별 불가 | 같은 위치·방향의 광원이 여러 개라 원래 광원을 특정하지 못한 것이다. 임의의 광원·패킷으로 재생하지 않는다. |
| 재생 실행 오류 | 오류와 JSON을 보존한다. 미검출 판정이나 표본 부족으로 해석하지 않는다. |

재생은 출발점과 첫 방향만 고정한 CPU 진단용 1 Ray다. 이후 반사를 저장 경로 쪽으로 강제하지 않으며, 검출·광량을 본 해석에 더하지 않는다.

## 5. 동일 센서 광량 비교

같은 Point에서 `광량 비교`를 열고 `비교 시작`을 누른다. 처음에는 기본값(8회, 회당 순방향 16,384 / 역추적 1,024, 허용 차이 5%)으로 시작한다. 이 실행은 원래 100만 Ray 결과를 그대로 재현하는 실행이 아니다.

`전체 요청 입력 일치`와 GPU 실행 증거를 확인한다. 이전 작업 결과 또는 입력 동일성 미확인이면 현재 조건으로 새 비교를 시작한다. 입력 일치는 센서 크기뿐 아니라 위치·방향·광원·재질·ROI·변환·해석 설정을 포함한다.

각 `순방향 상세 진단 · N회`와 `기존 종료 조건 상세 진단`을 펼친다. 회차별 0 검출·도달·제외 사유와 광량 변동을 확인한다. 비교의 순방향은 결정적 에너지 컷오프를 제거하고, 기존 종료 조건은 별도 실행으로 대조한다. 표본 예산·확률 경로가 있으므로 두 결과의 차이만으로 컷오프를 확정 원인이라고 단정하지 않는다.

미확정이고 표본 부족 안내가 나오면 `권장 표본 적용` 후 **다시 `비교 시작`**을 누른다. 적용만으로 실행되지는 않는다. 다른 조건과 허용 차이는 유지한다. 실행 오류·재생 오류·입력 불일치를 표본 증가로 해결하려 하지 않는다. `검증 JSON 저장`으로 `sensor-comparison.json`을 저장한다.

## 6. 원래 순방향 설정으로 상세 진단

Preview로 돌아와 같은 Point를 선택하고 `순방향 진단 준비`를 누른다. Point 기준 Receiver 1개가 활성화되고 Ray Tracing으로 이동하며 `순방향 원인 진단`이 켜진다. 센서 방향·수용각을 다시 수동 조정할 필요는 없다.

광원은 2단계에서 맞춘 등록 광원인지 확인한다. 기존 0 검출 실행에서 사용한 Ray 수·최대 반사·에너지 종료 조건을 유지하고 `Run Ray Tracing`을 실행한다. 결과 창의 `순방향 원인 진단`에서 Receiver 행을 펼친다.

| 진단 | 해석 |
| --- | --- |
| 도달 0, 연장선이 센서 면적 밖 | 진행 방향을 연장해도 센서 면적을 벗어난 구간이다. 실제 도달 수가 아니다. |
| 센서 전 형상 충돌 | 센서 면적 방향의 구간이 앞선 형상을 만났다. 전체 구간 수가 해당 대표 경로 하나의 차폐 횟수는 아니다. |
| 도달 > 0, 검출 0 | 뒷면 입사·수용각·ROI 제외 등 실제 제외 항목을 확인한다. |
| 검출 > 0 | 해당 Receiver에 양의 검출이 있다. 실물 대비 밝기나 화면/보고 표시가 다른지는 별도로 확인한다. |
| 진단·검출 집계 불일치 | 진단 수치로 원인을 확정하지 말고 JSON을 보존한다. |

`장면 이탈`은 더 만날 형상·수용 센서가 없는 종료 구간이며 특정 틈으로 나온 광량이 아니다. 구간 수는 반사를 포함하므로 발사 Ray 수와 다를 수 있다. 작은 광량의 안정성은 독립 반복으로 확인한다. `진단 JSON 저장`으로 `forward-receiver-diagnostics.json`을 저장한다.

## 7. 결과 보존과 후속 판단

기준 프로젝트, `forward-path-replay.json`, `sensor-comparison.json`, `forward-receiver-diagnostics.json`을 같은 조건의 한 묶음으로 보존한다. 선택 Point·실물 관찰 위치/방향과 실행 설정도 함께 기록한다.

계산 완료, 순·역방향 일치, 실물 일치는 각각 별도 판정이다. 0 검출이나 CPU/GPU 구현 정합만으로 빛샘 없음 또는 실물 검증 완료로 결론 내리지 않는다.
