# GPU 경계 탐색의 FP64 반복 연산 개선

## 적용 상태

복잡 CAD의 보조 BVH에서 같은 광선의 방향 판정과 위치 항을 한 번만 준비하도록
변경했다. FP64 경계 구간을 보수적으로 넓혀 후보를 찾은 뒤, 최종 삼각형 교차와
원래 BVH의 면 선택 순서는 기존 계산으로 확정한다. 물리 형상, 광원 분포,
반사율, Ray 수, 종료 정책과 광량 환산식은 바꾸지 않았다.

실험 후보의 TV 코너 CAD 100만 Ray는 고정 기준 1.499537초에서 0.738413초로
줄어 warm 중앙값 기준 2.031배였다. 직전 제품 0.865649초 대비 추가 개선은
1.172배다. 정적 제품 함수 반영 후 통합 526검사는 통과했지만 추가 엄격 반복
검사는 36/40으로, 기존 atomic 방출광의 합산 차이가 재현됐다. 독립 제품 측정은
CAD 100만 Ray 2.043배, CAD 1,000만 Ray 1.997배였고, 소형 확률 반사 조건도
1.984배여서 전체 최소 2배 목표를 아직 완료로 판정하지 않는다.

서버 재시작, 커밋, push, 패키지 설치와 시스템 설정 변경은 하지 않았다.

## 계산 변경과 정확도 보호

기존 각 노드의 `(경계 - 광선 시작점) × 역방향` 계산 대신, 광선마다 위치 항을
미리 준비하고 FP64 fused multiply add로 경계 구간을 구한다. GPU FP32로
내리지 않으며 fast math도 사용하지 않는다. 축 평행 여부와 역방향의 부호는
광선마다 정수 mask에 저장한다.

부동소수점 연산 순서 변경이 경계 누락을 만들지 않도록 각 축의 위치 항에
`(|시작점| + |루트 하한| + |루트 상한| + 2) × |역방향| × 2^-45`의 여유를
양쪽으로 준다. 루트 내부의 모든 자식 경계가 이 범위에 들어가며, 이는 FP64
반올림 오차를 포함하는 탐색용 구간이다. 삼각형 vertex를 이동하거나 실제
광학 간격을 바꾸는 방식이 아니다.

기존 유한 좌표와 방향 범위 제한, 극미소 방향의 원래 BVH 재탐색, 긴 거리 및
모서리·동률 후보 보호를 유지한다. 최종 삼각형 거리와 원래 leaf·분기 순서를
검사하는 slab 호출은 바꾸지 않았다. 보조 탐색이 불확실하면 원래 GPU BVH로
다시 계산하며 CPU fallback으로 숨기지 않는다.

제품 함수에는 실행 중 AST 변환이나 실험 script import가 없다. 실험 도구는
제품 함수에서 원래 보조 탐색을 복원해 대조하며, 복원된 AST hash도 고정해
기준 함수가 함께 바뀌는 것을 방지한다.

## 채택 전 비교

전달 경로는 source checkout `main@157230c68dabaf5dca1f82b1767793f9ef835a0a`와
미커밋 소스이며 장치는 NVIDIA GeForce RTX 3070이다. 준비된 GPU launcher
환경의 Python 3.13 x64, Numba 0.66.0, CUDA Toolkit 13.1을 사용했다.
같은 장면과 세션에서 모드 순서를 교대하고 첫 실행 및 warm 7회를 기록했다.
고정 기준은 같은 revision의 기존 수송·집계 함수와 개별 고정 전송을 재현한
비교이며 독립 checkout 전체나 LightTools 대비 속도가 아니다.

| CAD 100만 Ray 모드 | 첫 실행 초 | warm 중앙값 초 | 고정 기준 대비 | 직전 제품 대비 |
| --- | ---: | ---: | ---: | ---: |
| 고정 기준 | 5.947696 | 1.499537 | 1.000배 | — |
| 직전 제품 | 10.031548 | 0.865649 | 1.732배 | 1.000배 |
| 방향 판정만 재사용 | 6.646454 | 0.821436 | 1.826배 | 1.054배 |
| 방향 판정 및 보수 FP64 위치 항 | 6.853335 | 0.738413 | 2.031배 | 1.172배 |
| 방향 판정 및 추가 경계 padding | 6.592120 | 0.740617 | 2.025배 | 1.169배 |

추가 padding 후보는 더 빠르지 않고 형상 cache의 구간 조건까지 바꿔야 하므로
채택하지 않았다. 원래 경계 배열을 유지하는 보수 FP64 위치 항을 채택했다.
첫 실행은 JIT 비용 때문에 더 느릴 수 있으며 cold 실행 2배를 주장하지 않는다.

## 독립 제품 성능 측정

실험 factory를 주입하지 않고 기본 제품 함수를 새 프로세스에서 다시 측정했다.
두 범위 모두 같은 세션에서 고정 기준과 제품을 교대 실행했다. 원래 범위는
warm 11회, Ray 수를 10배 늘린 범위는 warm 7회의 중앙값이다.

| --- | ---: | ---: | ---: | ---: |
| TV 코너 CAD | 100,000 | 2.562배 | 1,000,000 | 2.043배 |
| Face 직접 도달 | 1,000,000 | 2.532배 | 10,000,000 | 2.768배 |
| 확률 2회 반사 | 1,000,000 | 1.984배 | 10,000,000 | 2.385배 |
| 갇힌 구조 상한 10 | 1,000,000 | 2.031배 | 10,000,000 | 2.388배 |
| 첫 면 흡광 상한 20 | 100,000 | 2.052배 | 1,000,000 | 3.198배 |
| 첫 면 흡광 상한 100 | 100,000 | 3.928배 | 1,000,000 | 5.553배 |

흡광 대조군은 첫 면에서 종료하므로 높은 상한의 속도비를 실제 1,000회 반사의
가속률로 해석하지 않는다. 확대 범위 7개는 2배를 넘었지만 원래 범위의 확률
반사 1.984배를 반올림해 2배 통과로 처리하지 않는다.

더 큰 TV 코너 CAD 1,000만 Ray는 warm 3회에서 기준 13.398361초, 제품
6.710398초로 1.997배였다. 첫 실행은 각각 17.283226초와 17.804029초다.
100만 Ray의 기준 1.494143초, 제품 0.731227초와 달리 큰 범위에는 여유 있는
2배 성능이 아직 확보되지 않았다. CAD 자동 처리의 CUDA 성공/시도는 각각
153/153과 16/16이다.

합성 갇힌 구조의 1억 Ray·반사 상한 10도 실행했다. 실제 표면 hit는 10억 회,
교차 질의는 11억 회였다. 첫 실행은 기준 56.277411초, 제품 26.178021초이며
warm 3회 중앙값은 49.452370초에서 19.206260초로 줄어 2.575배였다. 제품
warm 시간은 19.292042·19.206260·18.994869초다. `gpu_active`, CUDA 성공/시도
1,526/1,526, CPU hybrid와 resident fallback 0을 확인했다. 모든 실행의 이산
exact 및 광학 `1e-9` 검사는 통과했다. 이는 이 합성 장면의 결과이며 실제 TV
1억 Ray나 상한 1,000의 실행 시간을 보장하지 않는다.

### CPU 확대 범위 검증

같은 최종 제품 소스에서 CPU도 Ray 수를 10배 늘려 측정했다. 고정 기준의
4 worker와 현재 정책의 8 worker·자동 수송을 교대하고 첫 실행과 warm 3회를
기록했다. 7조건 모두 공개 결과가 bit 단위로 동일하며 교차·planner·reducer
fallback은 0이었다. 다음 시간은 warm 중앙값이다.

| 조건 | Ray 수 | 기준 CPU 초 | 제품 CPU 초 | 속도비 |
| --- | ---: | ---: | ---: | ---: |
| Face 직접 도달 | 10,000,000 | 13.848622 | 4.057534 | 3.413배 |
| 확률 2회 반사 | 10,000,000 | 14.244272 | 5.030695 | 2.831배 |
| 갇힌 구조 상한 10 | 10,000,000 | 88.557315 | 41.364457 | 2.141배 |
| TV 코너 CAD | 1,000,000 | 14.996479 | 6.726596 | 2.229배 |
| 첫 면 흡광 상한 20 | 1,000,000 | 1.286535 | 0.494860 | 2.600배 |
| 첫 면 흡광 상한 100 | 1,000,000 | 1.295968 | 0.501049 | 2.587배 |
| 첫 면 흡광 상한 1,000 | 1,000,000 | 2.950409 | 0.511943 | 5.763배 |

CPU 확대 범위는 최소 2배를 통과했다. CPU와 GPU 표의 시간이 서로 다른
동일 장면 세션에서 나온 만큼, 두 표의 시간을 나눠 CPU 대비 GPU 속도로
주장하지 않는다. 전체 목표의 미완료 항목은 GPU 일부 범위와 엄격 합산 반복성이다.

별도 register 상한 128·120·112·96과 device inline 변경은 약 0.863~0.873초로
직전 제품보다 빠르지 않았다. 보조 leaf에 2·4·8·16개 삼각형을 묶는 후보도
각각 약 0.971·1.105·1.384·1.874초로 느려져 채택하지 않았다. leaf 시험의
초기 count 오류는 실험 도구에서 수정하고 모든 면을 한 번씩 포함하는 검사와
정확도 검사를 다시 실행했다. 실패 로그는 최종 유효 측정과 별도로 보존한다.

## 정확도 검증 상태

채택 전 방향 판정 단독 9검사와 보수 FP64 및 추가 padding 조합 18검사가
통과했다. FP64 조합에는 2만 경계 구간의 보수성, 4천 교차의 면 ID와 거리 bit,
근접 면·ROI 사용자 속성·MIS·부분 batch·실제 1,000회 반사·중단·오류 후
미반영 suffix 복구를 포함한다. 제품 반영 후 핵심 scalar 10검사도 통과했다.

후보 성능 측정의 production preflight는 `available`, `strict_float64`,
`kernel_executed`, `kernel_verified` 모두 true, scope는 `production_ray_bvh`,
계약은 `strict_float64_bvh_v1`이다. 모든 모드는 `gpu_active`, CUDA 성공/시도
16/16, CPU hybrid 0, resident fallback 0이었다. 광원은 virtual plane이며
반사 상한 10에서 약 1,100만 회의 실제 교차 질의를 처리했다.

이산 결과 exact와 광학 출력의 절대·상대 `1e-9` 검사를 통과했다. Atomic
합산의 bit 단위 동일성이나 LT·실측 정합을 보장하는 결과는 아니다.

### 제품 통합 검사

제품과 검사 소스를 고정한 전체 60개 모듈의 526검사가 768.240초에 통과했다.
실패·오류·건너뛴 검사 모두 0이며 source/test/script hash가 유지됐다. 추가한
보조 leaf 크기, FP64 구간, 방향 mask와 조합 검사도 이 통합 실행에 포함한다.
memcheck는 6검사·32.061초·0 errors, synccheck는 2검사·22.163초·0 errors였다.

별도 seed 7169~7173 × 8,192/65,536 Ray × 4회의 더 엄격한 반복 판정은
36/40이다. 이산 결과는 전부 exact지만 네 실행의 방출광 합산이 33~41 ULP로
32 ULP 상한을 넘었다. 최대 상대 차이는 약 `5.71e-15`이며 허용 기준을
완화하지 않았다. Receiver나 광선 누락에 의한 큰 광량 차이를 뜻하지는 않지만
추가 정밀 반복 검사는 실패로 유지한다.

실패 항목은 `contribution_summary`와 `reflection_summary`의 반사 방출광이다.
해당 소형 MIS 형상은 새 복잡 CAD용 보조 BVH의 자동 선택 대상이 아니며,
과거 보고서에도 남긴 global FP64 atomic 합산 순서 문제다. 기본 경로의 높은
처리량과 엄격 반복성을 함께 만족시키는 후속 집계 개선이 필요하다. 과거 진단용
순서 집계를 통과한 것만으로 현재 기본 모드가 해결됐다고 처리하지 않는다.
